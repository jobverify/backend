# November 11 rewrite log fixes (policy v30)

Validation now accepts removal of the reproduced duplicated `The work model for the role is:` label and joining `Recruitment Fraud Warning.` to its notice with a colon. These are narrow editorial normalizations; arbitrary repeated facts, actor relationships, numeric thresholds, URLs, negation and qualification scope remain guarded. This does not enable unrestricted semantic paraphrasing.

After three failed corrections, adaptive mode skips 8 matching opportunities, then probes once. Failed probes extend the skips to 16, 32 and a maximum of 64; success resets the policy. Reason, fragment/assembly phase and qualification scope remain separate. Strict evaluation and `always` mode retain their correction opportunities.

Interrupted inference emits an `interrupted` result and increments `interruptedAttempts` without writing the job or consuming a persisted attempt. The job remains pending for a later run. Its model/correction request cost is included once even for shared generation, while unfinished duration is excluded from completed-description latency. External AbortSignal reasons retain their identity and are never annotated with another job's preview.

JSON summaries expose `processingStatus` (`complete`, `partial`, `cancelled`, `failed`) separately from classification handoff. Markdown reports are saved beside worker and aggregate JSON files and appended to GitHub's step summary. They distinguish publication from wording/layout edits, source fallback and correction acceptance. Rates are fractions, and missing historical telemetry is reported as unmeasured. Aggregate capacity includes runner-hours, peak/average simultaneous processing workers, timing sample count and publications per runner-hour. These intervals describe the rewrite process, not GitHub queue wait or billed job duration.

`JOB_DESCRIPTION_REWRITE_JOBS_PER_SHARD` now defaults to `auto`; unset, empty and `automatic` values also select automatic sizing. The planner targets two scheduling waves based on the configured parallel runner count, rounds partition counts to a power of two (maximum 256), and computes jobs per shard from the queue size. Small queues use fewer partitions to avoid allocating more shards than jobs; an empty queue keeps one preview shard. The supplied 27,826-job queue plans 128 partitions of about 218 jobs, with at most 64 parallel workers and two planned waves. Non-power-of-two parallel limits or account capacity can create additional waves. This is workload distribution, not a throughput or completion guarantee. Numeric job targets (for example `350`) and explicit shard counts remain supported. `capacityLimited` applies only to explicit numeric targets. Existing repository-variable overrides still take precedence.

Scraper concurrency defaults to `5` in both pipeline configuration and standalone parallel execution. Persisted admin settings and explicit environment values continue to override the default. Telegram delivery defaults to enabled; set `TELEGRAM_ENABLED=false` to disable it explicitly. Bot credentials and destination settings are still required for delivery. The scraper workflow declares these same defaults, and the example environment uses concurrency `5`.

Policy v30 and source-cache-v5 prevent older entries from satisfying fresh generation. Existing published fallback rows are not automatically requeued. The pinned model remains unchanged. Local protocol regressions verify these changes; a representative native before/after evaluation is still needed to establish actual rewrite quality or throughput improvement.
