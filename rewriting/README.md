# Local description generation on CPU

See [November 11 log fixes](LOG-FIXES-20261111.md) for current policy v30 behavior, automatic partition sizing, exponential correction cooldowns, interrupted inference accounting and explicit processing reports. This supersedes the historical default and cache-version notes below.

[LFM2.5-1.2B-Instruct QAD Q4_0](https://huggingface.co/LiquidAI/LFM2.5-1.2B-Instruct-GGUF/blob/430bea1a9fa4d973ce789c15f15e9ed214846f4f/LFM2.5-1.2B-Instruct-QAD-Q4_0.gguf) is the production description model. Its immutable revision, 695,755,488-byte artifact, SHA-256 and llama.cpp b11146 CPU runtime are pinned in [model.json](model.json). The worker verifies pinned assets before startup. Generation runs on the Actions runner without a paid inference API.

Policy `job-description-prose-v29` offers factual prose and qualification sections to the model for readability edits using only the current source. Numbers, negation, URLs, conditions and required/preferred scope constrain validation; their presence no longer freezes the surrounding paragraph or bypasses inference. Recognized metadata and separately planned headings remain source-owned. This includes inline ATS fields such as Position, Location, Time Type and Job Category even when no matching structured job field exists. Foreign demonstration facts are excluded because native testing showed that the small model could copy them into the current job. Generation uses greedy decoding. Production has no aggregate input/output word, character, byte or fact-count ceiling, and no minimum source word count. Blank or markup-only source remains ineligible. The older fact-plan, evidence-text, source-section and bounded-edit protocols remain available to explicit callers; their limits do not govern production prose rewriting.

Read-only template rendering and tokenization retry socket/reset/pipe failures at most twice, with 50 ms and 100 ms delays inside the original cancellation and deadline. The retry includes reading the JSON body. HTTP errors, malformed JSON, worker death and inference requests are not replayed. Per-job and aggregate `transportRetries` count the recovery attempts once across shared callers, including failures and timeouts. Exact source-response token counts are reused within a description's corrective attempts; each changed prompt still receives its own tokenizer count.

The client cleans source markup while preserving comparison operators, numbers and text. Longer editable text is separated at source headings and divided into blocks of at most 900 characters, independently of whether the whole description fits the model context. Short unprotected descriptions stay in one request. Every source span has an exact offset and retains inherited required/preferred scope. The client counts the actual chat template and the exact source-shaped JSON response with the model tokenizer. Each generation receives 1.5 times the response-source tokens plus 64 formatting tokens, at least 128 tokens, capped by the remaining 8,192-token context. Tiny fragments therefore cannot consume the entire context merely because it is available. Prompts occupying more than a quarter of the context and token-truncated output trigger physical splitting and complete-source regeneration. Splits preserve source text and Unicode characters. There is no aggregate source/output ceiling. A source-relative stream guard also rejects unsupported repeated runs. All chunks share the remaining workflow budget; production has no separate 180-second description deadline. Explicit callers can request a shorter timeout.

Only a complete sequence of source spans can publish. Final validation checks exact source reconstruction, offsets, each part and the assembled description. Protected and fallback text must equal its source verbatim. Conservative checks allow independent statement reordering, coordinated bare duties becoming bullets, unambiguous thousands separators, number spelling zero through nineteen and a small set of equivalent phrases. Harmless line wrapping is accepted only when every ordered canonical term keeps its scope, modality and negation. Numeric subject/value/unit/comparator associations, substantive term order, actors, conditions and qualification scope must survive. A generated trailing heading cannot alter the next block's scope. Physical fragments retain their original whitespace and boundaries, including splits inside identifiers; whitespace-only spans require no inference. Missing statements and added claims are rejected. Unrecognized paraphrases may be rejected even when a person would consider them equivalent. These lexical checks do not prove semantic equivalence or absence of hallucination; representative native output still needs review. `fullSourceCoverage` records structural coverage of the original spans, not a semantic quality score.

Before accepting or checkpointing an edited fragment, the client also validates it together with the accepted prefix and the untouched source suffix, using the same assembly and display formatting as final publication. A locally valid full stop or heading merge can otherwise change a statement that continues into another block. Such edits follow the bounded correction policy, then exact original-source fallback in production if still invalid; valid edits elsewhere remain available. Checkpoint prefixes receive the same contextual validation on resume. Generation telemetry distinguishes fragment rejections from contextual assembly rejections with `validationPhase`. Final complete-description validation still runs independently.

Known neutral role introductions and hyphenated nice-to-have/good-to-have wording normalize without changing factual checks. Numeric diagnostics compare number values and adjacent subject/unit/comparison terms. A completed content rejection, including generated HTML tags, can receive one corrective generation using the complete original fragment. The default adaptive policy tracks correction outcomes separately by rejection reason, fragment/assembly phase and inherited qualification scope. After three consecutive rejected corrections it skips the next eight matching correction opportunities, retaining the exact source, then permits one probe correction. A successful correction resets the state. Concurrent requests cannot all enter the probe at once; cancellation and transport failures release a probe without becoming factual rejections. Uncached editable blocks still receive their first model attempt. Rejected model text never becomes a fallback.

`JOB_DESCRIPTION_REWRITE_CORRECTION_MODE=always` restores one correction for every completed content rejection. Strict evaluation and readiness always retain that correction and never accept source fallback, regardless of adaptive history. Empty output and malformed completed JSON also retain their original correction and cannot become fallback success if still invalid. Prompts request Markdown without HTML. The user message contains only source text; inherited headings and the rejection reason stay in the system instructions. Correction shares the original deadline and cancellation signal. Runaway streams, interrupted responses, transport failures and cancellation cannot become fallback success. Correction mode participates in disk-cache and shared-generation identities.

Per-job and capacity `correctionRequests`, `correctionsAccepted`, `correctionsRejected` and `correctionsSkipped` count the adaptive policy's work independently of the 32-entry generation-detail limit. A correction accepted by validation may still preserve the original wording; it is not automatically a wording improvement. Shared work charges its cost once, including caller timeouts. Capacity separately reports `modelEditedDescriptionsPerHour`, `modelWordingEditedDescriptionsPerHour` and `modelLayoutOnlyDescriptionsPerHour`; wording rates are null when publication-level wording telemetry is incomplete.

Publication quality reports `modelEditedBlocks`, `sourcePreservedBlocks`, `protectedSourceBlocks` and `sourceFallbackBlocks`. Model edits additionally split into `modelWordingEditedBlocks` and `modelLayoutEditedBlocks`: the former changes the ordered words/digits after ignoring capitalization, punctuation and unambiguous thousands separators; the latter changes formatting only. These counts describe edits, not semantic quality. Aggregate `wordingMetricsRecordedDescriptions` gives their measured publication denominator; historical rows without these fields do not acquire invented word-edit judgments. Its `outcome` distinguishes `model_edited`, `source_preserved`, `source_fallback` and `metadata_only`. Unchanged model text counts as source preserved, not a model edit. Metadata-only input reports zero inference. Published fallback descriptions add warnings without increasing pending estimates or counting the same job twice. A published status means validated output was saved; it does not by itself establish a wording improvement.

Capacity also reports `modelWordingEditedDescriptions` and `modelLayoutOnlyDescriptions`, distinguishing publications with any changed wording from those with formatting edits only. Historical rows without wording metrics do not count as either. `reusedChunks` sums accepted checkpoint and fragment reuse, including on failed jobs; it is not an inference-request count or a measure of model quality.

Before final validation and rendering, dense plain-text lines longer than 600 characters receive paragraph breaks at existing sentence ends, after three sentences or about 420 characters. This also improves the display of retained source after a rejected rewrite. The pass changes whitespace only, preserves original source parts, and reports its insertions separately as `layoutParagraphBreaks`; these never increase model-edit counts. Exact fallback equality applies to the stored parts; the display may receive these whitespace breaks. Existing Markdown, code, tables, lists and short paragraphs retain their layout. The validator accepts an added full stop at an explicit blank source paragraph or source end, even when an unfamiliar heading joins its paragraph. Original sentence punctuation stays mandatory in the combined layout check, and a soft line wrap cannot authorize a new full stop. Changed actors, facts, conditions and qualification scope still fail.

Accepted prose becomes Markdown in description through the existing escaped renderer. Original sourceDescription, hashes and employer/filter fields are preserved. Canceled or incomplete work cannot replace the visible source. Physical model context, workflow time, memory and database document constraints still apply. Long documents may require many sequential generations and actual prose rephrasing costs substantially more inference than compact category decisions.

## Actions budgets and resume

The workflow registers once and previews the complete eligible queue. Repository variables configure `JOB_DESCRIPTION_REWRITE_SHARD_COUNT` (default 32), `JOB_DESCRIPTION_REWRITE_MAX_PARALLEL` (default 32), `JOB_DESCRIPTION_REWRITE_CPU_THREADS` (default 4) and `JOB_DESCRIPTION_REWRITE_CONCURRENCY` (default 4). Shard count must be a power of two up to 256; maximum parallel runners may be any integer from one to 256 and cannot exceed shard count. The workflow defaults to 32 shards and up to 32 simultaneous runners, subject to account and runner-pool capacity. More shards alone do not increase simultaneous inference capacity. GitHub concurrency limits and other workflows can reduce the number actually running.

Each runner starts one model server. CPU threads and CPU request slots are capped by actual CPU availability; request slots additionally have a hard upper bound of 32. Explicit GPU offloading permits up to 32 slots independently of CPU count and still requires a compatible checksummed binary. Increasing slots is an experiment, not a speed guarantee. Every slot keeps its own 8,192-token context; each server retains its 128 MiB prompt-cache cap. Defaults use up to 128 active descriptions over 32 runners. Outside the workflow, omitting shard count retains automatic sizing from `JOB_DESCRIPTION_REWRITE_JOBS_PER_SHARD` (default 1,000), rounded to a power of two up to 256; standalone planning defaults to up to 32 parallel runners, capped by the shard count.

`JOB_DESCRIPTION_REWRITE_RUNNER` can select an available larger Ubuntu 24.04 Linux x64 runner label compatible with the portable runtime; its default remains `ubuntu-24.04`. Set the thread/slot variables to the measured configuration for that hardware. This selects an existing runner; it does not provision hardware or enable GPU offload. More workers can increase total Actions usage. Startup, queueing and final reporting also affect elapsed workflow time. The workflow keeps its existing time budgets, factual validation and guarded publication behavior. Linux preflight runs partition, planning-CLI and aggregate-report checks before launching shards.

Partition ownership uses the immutable ObjectId suffix, so a source update cannot move a job between workers. All workers use the preview's retry cutoff. Validated rewrite caches, summaries, worker logs and rejection artifacts have partition-specific identities, including the one-partition case. One aggregate report waits for every worker, validates worker/model/policy identities, sums queue and quality metrics and saves `description-summary.json`. Missing or failed artifacts prevent successful handoff; cancellation and unexplained incomplete workers remain incomplete. Classification starts only after the rewrite workflow finishes.

This uses GitHub's supported [dynamic matrices](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/run-job-variations). Hosted jobs have a six-hour execution limit and matrices support up to 256 jobs; see [Actions limits](https://docs.github.com/en/actions/reference/limits). Partition size is a capacity target, not a guarantee for arbitrary source lengths or future model performance. A plan exceeding the configured target at its fixed shard count or the 256-partition limit records `capacityLimited`; a budget stop still reports remaining jobs explicitly. Runner concurrency changes elapsed time and can increase aggregate Actions usage.

Local callers still default to one request unless concurrency is explicitly enabled. Larger CPU machines can explicitly request eight or more threads/slots; smaller machines report the actual clamped configuration. Pipeline throughput must be measured on the actual runner; rephrasing does not guarantee that every queued job will publish within the workflow budget.

Scraping, generation and classification run in separate workflows. Each generation worker has a 350-minute job limit, a 345-minute step limit and a default 19,800-second (5 hours 30 minutes) runtime budget including setup. A queued worker's budget starts when its runner starts, rather than while it is waiting behind the matrix concurrency limit. Cleanup retains two minutes before the job deadline. JOB_DESCRIPTION_REWRITE_BUDGET_SECONDS overrides the total budget within that deadline; JOB_DESCRIPTION_REWRITE_MODE=off disables generation. An empty queue skips model cache restoration and startup.

A normal rewrite budget stop completes the pipeline stage and permits classification to continue with pending descriptions using their employer source. The summary still records budgetExhausted and interrupted work. Explicit cancellation remains incomplete; nonzero exits, worker/code/database errors and stale guarded writes remain failures. This does not override a GitHub job timeout or external cancellation.

Every startup readiness slot uses fresh strict inference (`allowSourceFallback: false`) and must pass validation, including any correction. Strict mode leaves factual statements in the model prompt and disables fallback; deterministic copying cannot make a failing probe pass. A quality rejection records `model_quality_unavailable`, `qualityStopped: true`, `handoffReady: true` and `processingComplete: false`; no production attempts are consumed and classification can continue. The admin pipeline displays the incomplete handoff as Completed with warnings. Genuine execution failures and cancellation retain priority.

The MongoDB queue reader materializes eight jobs per short indexed query and advances by _id. Each query finishes before inference; no database cursor remains open during multi-minute rewrites. Failed page reads still propagate as database errors. Interrupted work stays pending; transient item failures retry after one hour, up to three attempts. Deterministic validation failures have no scheduled identical retry. Failed records with a recorded different policy version become eligible and receive a fresh attempt budget through a guarded metadata repair. The v25 migration also retries active v24 publications with zero model-edited blocks and at least one protected block, so earlier copied descriptions receive the corrected inference path. The repair verifies the current source hash and guards the old policy and quality counters before resetting attempts. Accepted model edits, current-policy publications, baseline historical records and skipped records are not automatically requeued. A changed source displays the latest employer text until its replacement passes.

## Cache and diagnostics

V26 retains the targeted v24 source-copy migration introduced in v25. It does not automatically requeue published v25 rewrites. Its new policy/cache identity prevents older output or partial plans from satisfying a fresh v26 request.

LFM uses separate Actions keys for immutable assets and accepted prose rewrites. Validated outputs are cached in .cache/description-rewrites under policy v28 with the source-cache-v3 protocol. Identity includes the pinned model, full policy configuration, exact effective source and fallback mode; strict and production requests cannot share cache or in-flight work. The matching policy and Actions cache namespace change prevents earlier-policy outputs from satisfying a v28 request. Failed v27 records become eligible for the existing guarded policy-change retry with a fresh attempt budget. Accepted publications are not automatically requeued. Random worker aliases do not invalidate persistent entries. Responses are rebound to the requesting input hash and revalidated before a guarded write. Validated contiguous chunks are checkpointed with exact offsets and revalidated on resume. Fallback output never becomes a permanent accepted cache entry: only the validated prefix before its first fallback may be resumed, and the failed block is attempted again on a later generation call. Old caches cannot become new prose output. Memory caching is bounded to 128 entries per cache. The Actions save step skips absent or empty rewrite caches.

V28 adds a client-local, 128-entry cache of accepted fragments keyed by exact fragment text, inherited heading and fallback mode. Identical fragments in different jobs can reuse accepted model work, including unchanged accepted source, only after fragment and complete destination-context checks pass again. Rejected output and source fallback never enter this cache. A context mismatch triggers normal inference. Fresh evaluations (`cacheMode: refresh`) bypass this cache, and strict mode cannot reuse production entries. Reuse contributes to `reusedChunks` without increasing model requests or token usage; this optimization has not yet been measured on a native queue run.

Completed fragment rejections now reach the diagnostic collector before correction or fallback. `totalRejectedFragments` and `fragmentReasons` count these underlying rejected attempts separately from final rejected jobs (`totalRejected` and `reasons`). Both kinds share the same maximum of 10 samples and 65,536 bytes; final job samples can replace fragment samples. Shared generation emits each underlying fragment rejection once. Employer-text samples remain in the rejection artifact, while ordinary results and summary counters omit those excerpts. A successful publication may therefore have fragment rejection evidence without being a failed job.

GitHub Actions builds a separate `portable-avx2-v1` CPU runtime from the immutable b11146 source revision `7fe450e19305b828c199d602c23a8337aaa1f03b`. Registration and rewrite jobs use Ubuntu 24.04. Registration builds once with GCC 13 and debug symbols, or restores the exact build-script cache key, then uploads one runtime artifact for all shards. Native CPU tuning, AMX, AVX-512, AVX-VNNI, llamafile kernels, and dynamic CPU backend selection are disabled; AVX2/FMA/F16C/BMI2 remain enabled. Each shard verifies the binary checksum and build manifest, checks CPU features, restores the executable bit, and selects the custom binary before its fresh four-slot readiness probe. Missing or invalid artifacts fail without falling back to the previous prebuilt package. The model has its own cache key; accepted rewrite caches and publication validation are unchanged. Empty queues skip runtime preparation.

`scripts/portableRewriteRuntime.sh` runs only in Linux Actions. The runtime artifact retains `build-info.json`, `llama-server.sha256`, and `CMakeCache.txt`; shard summaries record the selected profile, source revision, executable hash/version, and native diagnostics. `JOB_DESCRIPTION_REWRITE_REQUIRE_CUSTOM_BINARY=1` prevents the workflow from using the old runtime if new pending work appears after an empty preview that skipped activation. The registration job runs the relevant workflow and diagnostic checks on Linux before preparing the runtime. This portable profile is a mitigation for the CPU-correlated startup crashes in the 1 November report; successful inference on the affected Xeon runners must still be established by the next Actions run. No Windows build or native test is required for this change.

Concurrent identical sources share one generation. Each caller retains its own deadline and cancellation; the underlying request is aborted when no callers remain. Usage and generation counts are attributed once. `cacheSource` distinguishes memory, disk and in-flight reuse. `cacheMode: 'refresh'` is an explicit client option for measuring fresh generation; it bypasses cached/partial output and in-flight sharing while storing newly validated results.

Summary artifacts and console results omit source/completion bodies and report configuration, warnings, token use, latency, memory and queue progress. Capacity metrics count edited descriptions, edited blocks, preserved/protected/fallback blocks and cache reuse separately. Median and p95 latency include only results charged fresh inference; deterministic rendering and cache/in-flight reuse cannot make inference latency appear faster. Aggregate throughput uses the whole workflow's observed time range. Per-job telemetry includes source offsets, source and prompt tokenizer counts, finish/split reasons and durations for at most 32 generations, plus aggregate usage and reused chunk counts. Bounded-edit-specific metrics only apply to callers selecting that protocol.

A separate description-rejections.json artifact contains at most ten rejected examples, capped at 64 KiB, with at most two samples per reason. Samples identify probe versus production phase; production failures can replace same-reason probe samples. A new rejection reason can replace a duplicate-reason sample when the set is full. Bounded raw completion previews survive prose validation, partial JSON parsing and incomplete streams; precise failing statement details are included when available. It excludes raw exception objects and configuration objects; only the bounded sanitized failure fields described below are retained. The summary contains reason counts and the sample count, not those text excerpts. These examples follow the existing 14-day Actions artifact retention and repository access rules.

Probe samples additionally retain the synthetic readiness source as `probeSource`, separately from the failing statement in `sourceContext`. Validation evidence identifies fragment versus assembly phase and inherited section context. Assembly failures retain their actual failing candidate excerpt instead of the last unrelated model completion.

Failure diagnostics now retain a bounded, sanitized `errorDiagnostic` on failed job results and an `error` on their rejection samples. These include original exception type, message, stack locations, bounded causes, request phase/route, HTTP status, and source offset when available. Credentials, quoted response excerpts, request/response objects, and environment objects are excluded from these new fields. Raw exception objects are never serialized. Each readiness slot emits start/finish events and retains its timings and outcome in `workerProbe.probes`, including when readiness fails before processing the queue.

`workerRuntime` records executable SHA-256/version, runtime tag, operating system, CPU model/features, and native debugger availability. The worker log begins with its actual startup arguments and retains runtime information at verbosity 3. On Linux, `JOB_DESCRIPTION_REWRITE_NATIVE_BACKTRACE=1` requests GDB capture; the Actions rewrite job enables it and attempts to prepare GDB. A bounded launch preflight must run the exact helper, observe a running inferior, and verify that JSON, spaces, empty arguments and shell metacharacters survive unchanged before debugger capture is enabled. GDB's startup shell stays enabled to decode the escaping supplied by `--args`. The registration job installs native test tools and requires the real argument-preservation and crash-capture tests to run before launching shards. An unavailable or unusable debugger is explicitly recorded and direct launch remains available. Local callers use direct launch by default. GDB disables automatic scripts and symbol downloads and records up to 24 stack locations for each of at most 16 threads, capped at 32 Ki characters, without argument values or locals. Fatal native signals remain failures, and cleanup stops the debugger process group. The shard artifact includes `description-worker-N.log.native.json`; no raw core dumps are uploaded. A missing native stack is reported explicitly. Debugger execution can affect timings, so native performance comparisons should use the same launch mode.

The generic publishing filter rejects missing, blank and empty-HTML employer descriptions before persistence. Historical empty-description records are hidden from public lists, detail pages, saved-job results and counts. An explicitly empty source cannot be replaced with generated display text. Scraper diagnostics retain filteredEmptyDescription, and raw dry-run captures remain available for inspection.

## Three-second latency target

`descriptions:latency` compares one versus four concurrent requests on the actual native runtime, without MongoDB or publication:

```powershell
npm run descriptions:latency -- --input ../artifacts/rewrite-run-1418e50a/native-benchmark-input.json --output ../artifacts/rewrite-latency-20261029/native-report.json --target-ms 3000 --budget-seconds 1800
```

Each configuration starts one worker, disables idle unloading, warms it once, then measures fresh complete rewrites, disk-cache replay and memory-cache replay separately. By default this model-quality benchmark uses strict inference with source fallback disabled. `--allow-source-fallback` explicitly measures production-style adaptive correction and publication behavior instead. Fresh measurements bypass result caches and request coalescing; cached phases replay only accepted fresh cases without fallback. Reports retain original and accepted descriptions, quality counts, correction counters, fallback descriptions, `wordingEdited` and `wordingEditedPerHour`, acceptance/rejection counts, model requests, p50/p95/max duration and throughput. Requested concurrency and actual slots/threads are separate. `sampleMeetsTarget` requires every fresh source to pass within the target; in production-style mode that can include preserved-source publications, so inspect wording yield separately. Startup, asset preparation and warmup are separate. The target never truncates output, weakens validation or becomes a three-second cancellation limit.

Compare correction modes on the same inputs and hardware, with separate output directories and production fallback explicitly enabled:

```powershell
npm run descriptions:latency -- --input test/test-data/rewrite-throughput-jobs.json --output .cache/description-throughput/always/report.json --concurrency 1,4,8 --threads 8 --correction-mode always --allow-source-fallback --budget-seconds 1800
npm run descriptions:latency -- --input test/test-data/rewrite-throughput-jobs.json --output .cache/description-throughput/adaptive/report.json --concurrency 1,4,8 --threads 8 --correction-mode adaptive --allow-source-fallback --budget-seconds 1800
```

The three-case fixture includes the supplied Sattva description plus required/preferred and negation examples. It is a smoke sample and may not trigger an adaptive cooldown. Use a larger representative exported batch, with enough time to finish every configuration, for steady-state throughput comparisons. Native v29 speed and wording quality require verified local assets and actual hardware measurements; HTTP regression timings are not native performance evidence. The repeated-failure regression reduces 40 requests to 24 for 20 blocks while retaining exact source, but does not establish a queue-wide speedup. Existing published v25-v28 descriptions are not automatically requeued by this policy update.

Verified local model/runtime assets are required by default; missing assets produce a blocked report without a download attempt. Use `--assets-dir` for another local cache, or explicitly opt into `--download-assets`. Hardware results from fixture tests are not native performance evidence. A local smoke run does not replace the one-versus-four-slot latency benchmark or establish the three-second target for v22.

Request latency excludes recording the benchmark artifact; aggregate throughput includes that I/O. Warmup failures retain their request counts and bounded diagnostics. `nativeInferenceAttempted` records that generation was attempted, while `nativeInferenceExecuted` is `null` when an attempted warmup fails without observed output, `true` when output is observed, and `false` when missing assets prevent any attempt.

For a GPU-capable machine, supply a compatible llama.cpp b11146 build and its binary SHA-256:

```powershell
npm run descriptions:latency -- --input jobs.json --gpu-layers all --binary C:/runtimes/llama-server.exe --binary-sha256 YOUR_BINARY_SHA256 --assets-dir .cache/description-rewriter
```

GPU layer settings accept `0`, a nonnegative layer count, `all` or `auto`. A positive/automatic offload request cannot silently select the pinned CPU package through the CLI; a custom binary and checksum are required. The binary checksum verifies the caller-selected file, not GPU availability or compatibility. Confirm actual offload in the worker log before interpreting a result as GPU performance. No GPU driver, runtime or remote service is installed automatically.

Production/local rewriting accepts `JOB_DESCRIPTION_REWRITE_GPU_LAYERS`, `JOB_DESCRIPTION_REWRITE_BINARY` and `JOB_DESCRIPTION_REWRITE_BINARY_SHA256` as explicit opt-in settings; defaults remain CPU. A single worker stays loaded throughout its run and prompt-prefix reuse is enabled. GitHub still defaults to four requests; set the repository variable `JOB_DESCRIPTION_REWRITE_CONCURRENCY` to `1` only after comparing latency and throughput on that runner.

The full dry-run benchmark defaults to --model 9000 and the configured production client. Local source/output reports and resumable evaluations reject changed model/policy/source identities. Experimental trial prompting is documented separately in [TRIAL.md](TRIAL.md); it is not the production publication protocol. Windows speed and earlier model results do not establish Ubuntu throughput.
